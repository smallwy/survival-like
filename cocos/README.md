## 打开就能跑

工程骨架与美术都已生成/同步好（场景、设计分辨率、2D 模块集、35 张图），
**不需要手动建节点、也不需要手动导入美术**。

1. **Cocos Dashboard → 项目 → 添加**，选中本目录 **`cocos/`** 本身
   （不是仓库根目录 `survivors-game/`）。
2. 用 **3.8.8** 打开。首次会导入资源，约 1–2 分钟，同时生成 `library/ temp/ local/`
   （都在 `.gitignore` 里，不会污染 git）。
3. 场景 **`Dive`** 会自动打开（`settings/v2/packages/scene.json` 里记了当前场景）。
   若没自动打开：资源管理器里双击 `assets/scenes/Dive.scene`。
4. **点 ▶ 运行。** 先进**主界面**（探照灯 + 峡谷 + 三台潜航器卡片），
   选一台 → `Enter` 或点「开始下潜」才真正进战斗。

> **还没跑过 `sync_art.py` 也不会报错**，游戏照跑 —— 只是敌人是几何剪影、
> 背景是纯色块、主界面的立绘框是空的（见「美术」一节）。

画面结构是：`Canvas` → `Game`（挂着 `DiveGame` 组件）+ `Camera`。

> **万一场景没生成成功**（或你想从头搭）——手动三步：
> ① 项目设置 → 项目数据 → 设计分辨率设成 `1304 × 749`；
> ② Canvas 下建空节点 `Game`，position `(0,0)`，挂上组件 `DiveGame`；
> ③ 运行。
> 组件挂在 Canvas 上或它的**子节点**上都可以（会自动往上找带 `UITransform` 的那层）。

**操作**

| 场合 | 按键 |
|------|------|
| 主界面 | `1` / `2` / `3` 直选潜航器，`←` `→` 循环，`Enter`（或点「开始下潜」）下潜 |
| 战斗 | `WASD` / 方向键移动，`空格` 或 `Shift` 排气爆发（边沿触发，按住不连发） |
| 战斗中 | `Esc` 重开一局（换艇要回主界面：结算屏的「返回主界面」） |

**组件可调项**：`designW / designH`（1304 / 749）、
`seed`（**第 n 局用 `seed + n`**，所以世界线固定可复现 —— 报问题时说"第几局"就够了）、
`subIndex`（0 灯艇 / 1 刺鳐 / 2 深潜者；**只在没有存档时**用作默认，有存档时默认选中上次用的那台）。

> 设计分辨率用 **fitWidth**（`settings/v2/packages/project.json`）。
> 想改成 fitHeight 就在项目设置里调，组件按 Canvas **实际**尺寸自适应，不会错位。

## 单一真源（一）：逻辑与数值 `shared/`

引擎无关的数值表与模拟逻辑只有**一份手写源**：项目根的 `shared/`。
两个前端消费方式不同，原因是硬约束：

```
shared/**  ──(直接引用 @shared/* 别名)──▶  web/      ← Vite 允许引用 root 之外的文件
           └──(tools/sync_shared.py 复制)──▶  cocos/assets/scripts/shared/**
```

**为什么 Cocos 必须复制**：Cocos Creator 只编译 `assets/` 目录下的脚本。
`assets/` 之外的 TS 源码不会进构建产物（外部目录只能放 `.d.ts` 类型声明，
靠 tsconfig paths 被找到；运行时模块不行）。

复制出来的文件带 `GENERATED FILE` 横幅，并且可以检出漂移：

```bash
python tools/sync_shared.py            # 写入/更新副本
python tools/sync_shared.py --check    # 只检查漂移（漂移则 exit 1，并指出第几行不同）
```

于是"两份代码不一致"是**可以被脚本抓到**的，而不是靠人记得。
改平衡/数值**只改 `shared/`**，然后跑一次 `sync_shared.py`。

## 单一真源（二）：美术 `web/src/assets/`

美术同样只有一份手写源（`web/src/assets/`），用脚本同步进 Cocos：

```bash
python tools/sync_art.py            # web/src/assets → cocos/assets/resources
python tools/sync_art.py --check    # 双向漂移检测（源变了 / 副本被手改，都能查出来）
```

同步时会做两处**必要的**转换（理由都在脚本头部注释里）：

| 转换 | 为什么 |
|------|--------|
| 五层背景 `.webp` → `.png` | `cc.d.ts` 里 `SUPPORT_TEXTURE_FORMATS` 含 `.webp`，但那是**引擎运行时**支持的格式，不等于**编辑器导入器**支持。这一点在沙箱里无法验证，而一旦不支持，症状是图丢失 —— 转成 PNG 的代价是 0.37 MB → 3.6 MB，换零风险 |
| 道具立绘 `1200×600` → `600×300` | 立绘框在 sim 坐标里只有约 268×96，1200 宽是显示尺寸的 4.5 倍，纯浪费。600×300 正好是**显示尺寸的 2 倍**（高分屏够用），9.83 MB → 2.80 MB。这是**质量中性的降采样**，不是拿画质换体积 |

`--check` 靠 `tools/art_manifest.json` 里记录的源/目标双哈希核对，所以**不需要重新编码**
（Pillow 升级也不会造成假漂移）。

### 「游戏需要哪些美术」这张表放在 `shared/dive/artKeys.ts`

不是各引擎各写一份。写两份必然漂移，而漂移的症状是**"某个东西没图"—— 它不会报错**，
只会静默退回几何剪影，很难注意到。放在 `shared/` 之后，`verify_cocos.py` 能 require
**运行时同一份表**去跟磁盘对账，于是"表里加了 id、美术却漏了"在离线阶段就会红。

key 全部从既有表推导：`ENEMY_TEX`（敌人）、`LAYERS` 下标（背景）、
`WEAPON_DEF`/`RELIC_DEF` 的 id（商店立绘）、`SUB_ART_PATH`（潜航器）。

### 美术是**增量**，不是前置条件

`resources/` 下缺哪张图就静默跳过，渲染层自动退回 `Gfx` 画的几何剪影。
所以"打开工程 → 点运行"这件事不依赖任何美术步骤。

> **首次在编辑器里打开后**，`assets/resources/**` 下会生成一批 `*.png.meta`。
> 那些 meta **要入库**（它们记录资源的 uuid，跨机器必须稳定）——
> `.gitignore` 已经确认不会忽略它们。

## 主界面（潜航器三选一）

移植自 `web/src/scenes/TitleScene.ts`，但**做成 `view/Title.ts` 里的一个类**，
而不是第二个 Cocos 场景。理由：

- Cocos 的 `director.loadScene()` 要求目标场景在构建列表里；而"编辑器里点 ▶ 跑的是
  **当前打开的那个场景**"。加第二个 `.scene` 会把已经做好的「打开工程点运行」
  变成"你得先知道要打开哪个场景"。
- 主界面只是个静态菜单。`root.active = false` 之后它真的不参与渲染与更新，
  "独立场景省 CPU"这个原始动机照样达到。
- 它因此与 `Hud.ts` **完全同构**（纯类 + 自建节点树，由主组件分派 `update`），
  复用同一套已验证的交互模式。

画面元素：深渊竖向渐变底 → 峡谷岩壁（只有霓虹轮廓 + 近黑填充，人字形收拢）
→ 探照灯光锥（唯一光源，摇曳靠改 `UIOpacity` 与节点 x，不重画几何）
→ 5 只自发光水母（色相避开 UI 青蓝，否则会被读成 HUD 元素）
→ 浮游微粒 → 标题字（发光靠低透明副本，不用 ADD 混合）→ 三张潜航器卡
→ 舱窗网格 + 扫描线（α ≤ .06，刻意排在 UI **之上**做"隔着玻璃"的暗示）。

卡面上的特性行**收益绿、代价橙**（`subFeatLines`）—— 三台是机制差异不是数值差异，
每台都带一条同轴代价，否则玩家永远只选"最强的那个"。

与 web 的两处刻意不同：

| 差异 | 原因 |
|------|------|
| **不设 `fontFamily`** | web 用 `Noto Sans SC / PingFang SC / Microsoft YaHei` 三档回退，那是 CSS 语义，原生平台不保证等价；"字体没生效"是看不出来但一直不对的那类问题。先用引擎默认系统字体（`Hud.ts` 也一样），等接入字体资源再统一 |
| **多了一行纪录**（顶部） | 存档是新增的（见下）。纵向布局在 322(副标题) / 349(装饰线) / 358(卡顶) 之间没有空档，而 0–180 整条是空的，所以放顶部 |

> 「装置坞」按钮是**诚实的占位**：点开只说明"港口与装置升级树还没做"，
> 不假装有内容。弹窗开着时卡片与按钮不响应点击 —— 否则"点一下关闭"顺手会把选项也换掉。

## 震屏

模拟层抛 `{t:'shake', ms, intensity}` 事件（`shared/dive/world.ts`），渲染层只负责抖。

数值与原版一致，五处触发：Boss 震击 `220/0.008`、暴击命中 `90/0.0022`、
换层 `260/0.004`、鱼雷爆炸 `130/0.006`、击杀按体型分档（Boss `320/0.012`、
大水母 `120/0.0035`、**普通小鱼不震**）。

语义**照抄 Phaser**（`web/node_modules/phaser/src/cameras/2d/effects/Shake.js`）：

- 幅度 = `intensity × 视口宽/高`，**整段时长内不衰减**，到点直接归零。
  它不是"逐渐平息"，就是定幅随机抖动然后戛然而止 —— 看着很"脆"，但那是原版手感。
- **已经在震时忽略新震**（Phaser 的 `force=false` 语义）。这条是刻意设计的：
  每秒几十次的暴击震屏不会叠成持续抖动，所以"只给暴击震"这个取舍才有意义。

抖动加在 **`WorldRoot` 节点**上，而不是相机上 —— 于是世界各层一起抖、
**HUD 天然不跟着抖**。这比 web 好一点：Phaser 的相机震屏会把 `scrollFactor=0`
的 HUD 一起晃（`GameScene.ts:3159` 有专门注释吐槽过这件事）。

一处**已知近似**：Phaser 还会再乘一次 `camera.zoom`（世界相机 `zoom=1.25`），
即它的实际位移比 `intensity × 宽` 略大。这里按屏幕像素直接给
（1304 宽时 `0.008` ≈ ±10px）。若目视觉得比 web 震得轻，改 `DiveGame.shake()`
的注释里指出的那一处即可。

## 跨局纪录（本地存档）

**web 侧没有任何存档** —— `DiveScene.ts` 全文件不含 `localStorage`，也没发过网络请求。
仓库里 `server/` 倒是有完整的 `/api/save` `/api/load` `/api/meta` `/api/leaderboard`
（Go，491 行），但**前端从未调用过**，是空壳。

所以这一块是**新增功能，不是移植缺口**。选择先做**本地档案**、不接服务端：

- 单机进度不需要账号体系；接服务端等于顺带引入登录/身份/网络失败态，那是另一个量级。
- `sys.localStorage` 在 Web 上就是 `window.localStorage`，在原生平台落到各平台本地存储
  —— 一份代码全平台可用。

存什么：`bestBiomass`（最佳带出生物质）、`bestLayer` / `bestWave`（最深层与那一层的最远波次）、
`runs`（局数）、`cleared`（击杀过守望者）、`lastSub`（上次用的艇）。
**局内状态一律不存** —— roguelike 的一局本来就不该续，"半途退出"因此没有损失语义，
也不存在"读档回到一半"的边界情况。

三处刻意的设计：

| 设计 | 为什么 |
|------|--------|
| 逻辑在 `shared/dive/profile.ts`，读写只在 `view/save.ts`（40 行） | 纯函数无引擎依赖 → **进得了无头冒烟测试**（`[6]` 段 10 条断言）。换存储后端时逻辑一行不用改 |
| 逐字段回退，不整体丢弃 | 读到旧版本/被手改成非 JSON 时，一项不合法只重置那一项。否则用户会莫名其妙丢掉所有纪录 |
| 层与波次**成对**比较 | "第 3 层第 2 波"比"第 5 层第 0 波"浅，单看波次没有意义 |
| 「带出生物质」溺水按 0 记 | 与结算屏公式一致（`win ? floor(biomass × mult) : 0`）。否则"死得越深纪录越高"，档案变成反向激励 |

顺带修掉一个模拟层的真 bug：`showResult()` 原本**不幂等**，而 `drainOxygen()` 判定溺水后
当帧的 `updateWave()` 仍会跑完 —— "最后一波最后一个敌人被打死的那一刻氧气刚好归零"
会**同帧**再抛一次 `runCleared`，把 `win` 覆盖成 true，结算屏显示"上浮成功"而这一局实际
是淹死的。现在 `showResult` 幂等，视图侧 `finishRun()` 再兜一个 `runSaved` 标记。

## 坐标系与镜头

模拟层沿用 Phaser 的「**左上原点、y 向下**」，而 Cocos 2D 是「**左下原点、y 向上**」。
转换只发生在三处，模拟层对此一无所知：

| 位置 | 规则 |
|------|------|
| 图元绘制 | 全走 `Gfx` 包装，内部自动 `y → H - y` |
| 节点定位 | `(x, y) → (x, H - y)`；`WorldRoot` 锚点 `(0,0)`、尺寸 `W×H` |
| 旋转 | `node.angle = -θ°`。依据：引擎实现是 `Quat.fromAngleZ(this._lrot, val)`，即 **`node.angle` 逆时针为正**，与 sim 正好反号 |

因为只有这一条规则，"sim 坐标画到哪里"不会出现第二种解释。
`view/` 里的绘制代码因此与原 Phaser 绘制代码几乎同构 —— 这是刻意换来的可对照性。

**镜头缩放不用相机。** `CAM_ZOOM = 1.25` 是通过**缩放 `WorldRoot` 节点**做的，
不是改相机。原因见「已知坑」第 5 条。节点缩放还能顺带白拿一个正确行为：
HUD 挂在 Canvas 下、是世界根节点的**兄弟**，天然不跟着缩。

暗角/压暗层（`gVeil`）也画在**世界坐标**里，而不是做成全屏节点 —— 因为 web 侧有一条
铁律：「暗幕只能压暗地形，敌人/气泡/玩家必须画在它之上，否则深渊层（可见度 10%）
会把 gameplay 信息一起吃掉」。做成画在实体之上的全屏节点就必然违反它。
现在的做法是"按当前可视矩形在世界坐标里画暗角"，效果等价且不破坏该规则。

## 验证：能证明什么、不能证明什么

```bash
python tools/verify_cocos.py      # 一条命令，7 个阶段
```

| 阶段 | 内容 |
|------|------|
| 真源漂移检查 | `shared/` 与 `cocos/assets/scripts/shared/` 逐文件比对 |
| 编译模拟核心 | `shared/dive` → CJS（`tsc --strict`） |
| 无头冒烟 | 真跑 120s 模拟 + **31 条不变量断言**（含跨局档案纯函数那 10 条，见下） |
| 视图层类型检查 | `cocos/assets/scripts/**` 全量过 `tsc --strict`，**优先用引擎自带的 `cc.d.ts`** |
| 美术完整性 | 源↔副本哈希一致；代码会去要的每个 key 在磁盘上都有（反向也查残留） |
| 工程资源完整性 | 场景 `__id__` 引用、`_id` 唯一性、**脚本类 id ↔ `.ts.meta` uuid 是否对得上**、压缩 uuid 算法往返自检 |
| 模块图自检 | 源码里每条相对 import 都能命中磁盘上的真实模块；且**编辑器增量编译的解析表里没有 `__unresolved_*`** |

最后这一条是**专门堵假绿**的：它抓的正是"源码全对、编辑器里却全黑"（见「已知坑」第 16 条）。
其中"产物那一半"要求编辑器至少编译过一次本工程（`temp/` 存在），没跑过就只能查静态那一半。

### 类型检查优先用**引擎真声明**，这件事很关键

脚本按这个顺序找 `cc.d.ts`：环境变量 `COCOS_ENGINE_DTS` → 本机 Cocos 安装目录
（`C:/ProgramData/cocos/editors/Creator/<版本>/…/bin/.declarations/cc.d.ts`）→
都找不到才退回 `tools/cocos_cc_stub.d.ts`。

**为什么值得单独说**：手写的声明桩是"按我的理解"写的，它只能验证"代码是否符合我的
假设"。本项目**真的因此漏过一次** —— 桩里我顺手写了 `Camera.zoom`，于是检查全绿；
换成引擎真声明后立刻报错：Cocos 3.8 的 `Camera` **根本没有 `zoom` 属性**，
只有 `orthoHeight`，而那是 `Canvas` 组件托管的状态。**桩越像真的，假绿越危险。**

**✅ 能证明**
- 模拟核心与 `web/src/scenes/DiveScene.ts` 的行为一致：5 层波次推进、清波 → 商店 →
  决策 → 结算、氧气收支、死亡路径、**同 seed 得到完全相同的世界线**（确定性）；
- 视图层**没有用错模拟层 API，也没有用错引擎 API**（字段名拼错、参数个数不对、
  属性根本不存在……）—— 这是移植里最容易出的错，而且只有 `tsc` 抓得住；
- 真源与 Cocos 副本零漂移；美术亦然，且"表里加了 id、图却没同步"会红；
- **工程骨架自洽**：打开编辑器不会遇到 Missing Script / 悬空引用。

**❌ 不能证明**
- 引擎 API 的**运行期真实行为**。类型只说明签名对 ——
  `Graphics.ellipse` 画出来什么样、节点缩放与 UI 相机的配合、Sprite 的混合模式，
  这些都在类型的外面。
- **画面是否真的画对了。这一条只能由你打开 Creator 点运行目视确认。**

所以：`verify_cocos.py` 全绿 ≠ 能跑；它绿了只说明"进编辑器之前，代码与工程骨架该对的都对上了"。

## 已知坑（都是"注入 Creator 后才会暴露"的那类）

1. **运行时 `new Node()` 的 layer 是 `DEFAULT`，而 Canvas 的 UI 相机只渲染 `UI_2D`**
   → 漏一处就是"画面上什么都没有"。所以 `view/` 里所有建节点都走
   `mkNode()` / `mk()`，它强制继承父节点 layer。**场景里手写的节点同理**：
   `Dive.scene` 里 `Game` 节点的 `_layer` 必须是 `33554432`（UI_2D）。
2. **Sprite 要 `trim = false`。** `trim` 默认 `true`，会按"N 宫格/图集裁剪后的区域"
   渲染；而立绘的 contain 缩放是按**原图**比例算的，裁了就偏。
   同理取素材宽高比要用 `SpriteFrame.rect`（原图矩形），不要用 `originalSize`。
3. **敌人贴图必须按素材宽高比定尺寸，不能拉成正方形。** web 侧为此踩过一次并留了
   记录：素材实际比例是 swarm 1.99 / drift 1.54 / dash 0.55，旧代码统一
   `setDisplaySize(s, s)`，于是"一条 2:1 的长鱼被压成方块"，玩家看到的是**黑块**。
   现在的规则：长边 = `r × 3.1`，短边按比例算（只改视觉，不动碰撞半径）。
   另外**显示尺寸 < 26px 时退回矢量** —— 小尺寸上贴图细节会变成噪声（水母 60% 面积
   是细触须，缩到 14px 就糊成"白色小飞虫"）。
4. **Label 的锚点要跟着对齐方式走。** 在 `overflow = NONE` 下 Label 内容尺寸自适应
   文本，锚点 `(0.5, 0.5)` 意味着"文本中心落在节点位置" —— 于是右对齐的数字
   右边缘会随位数漂移（`10` 和 `100` 右边不一样齐）。锚点设 `0 / 0.5 / 1` 才是真贴边。
   这是 Phaser 侧 `setOrigin` 干的同一件事，移植时最容易整片漏掉。
5. **Cocos 3.8 的 `Camera` 没有 `zoom` 属性。** 只有 `orthoHeight`，而它是 `Canvas`
   组件自己托管的状态 —— 去改它等于跟引擎抢同一份状态，什么时候被覆盖回去取决于
   Canvas 的实现时机，而这条在沙箱里验证不了。所以镜头缩放改成**缩放 `WorldRoot` 节点**。
   （`Dive.scene` 里曾经序列化过 `"cam"` 指向相机，已一并删掉；相机仍由 Canvas 的
   `_cameraComponent` 持有，不会悬空。）
6. **Graphics 纪律**：每个图元必须建好路径立刻 `fill/stroke`，且配色紧贴其前。
   不能"先 `rect` 攒着、中途换色"—— 那会把前一个图形也染成新色。
7. **别把局部变量命名成 `col`**：`view/` 里的颜色构造函数就叫 `col`（来自 `Gfx`），
   同名局部变量会把它遮蔽掉，报错形式是莫名其妙的 "Type 'Number' has no call signatures"。
8. **全屏底色不能写死 `(0, 0, W, H)`**：设计分辨率与 `W×H` 宽高比不一致时，
   弹窗两侧会露出清屏色。`Hud.pageFill()` / `DiveGame.drawBg()` / `Title.layout()`
   都按 Canvas 实际尺寸外扩了。
9. **`cocos/tsconfig.json` 不要用于 CI**：它 `extends ./temp/tsconfig.cocos.json`，
   而 `temp/` 由编辑器首次打开时生成，沙箱里不存在。离线检查的 tsconfig 由
   `tools/verify_cocos.py` **现场生成**（因为 `cc` 声明的位置是机器相关的，
   静态文件必须"按机器改"，那就一定会有人忘了改、然后得到一份假绿）。
10. **`.creator/` 不能加进 `.gitignore`**：里面的 `default-meta.json` 是**工程配置**
    （图片按 sprite-frame 导入），官方 `empty-2d` 模板就是入库的。
    （本目录的 `.gitignore` 里有注释专门标注这一点。）
11. **场景里引用用户脚本用的是脚本资源的压缩 uuid**，不是完整 uuid。
    所以"用文本生成一个预挂组件的场景"这件事，成败全看压缩算法对不对；
    算错的症状是编辑器显示 **Missing Script**（画面还能跑，但组件不生效）。
    算法在 `tools/cocos_uuid.py`，`verify_cocos.py` 每次都会跑自检 + 引用比对。
12. **`.gitignore` 不支持行内注释。** 写成 `/library/   # 缓存` 时整行（含空格和 `#`
    后面的中文）被当成一条规则，于是**永远匹配不上** —— 编辑器一打开工程，
    `library/`（36 MB）、`temp/`、`profiles/` 就成片涌进 `git status`。
    注释必须独占一行。（本目录的 `.gitignore` 顶部有醒目警示。）
    **排查陷阱**：`git check-ignore -v <路径>/`（带尾斜杠）会返回 exit 0 并打印一个
    空模式，**看着像"已忽略"其实没有**；要用 `git ls-files --others --exclude-standard`
    或对不带斜杠的**文件**路径判定。
13. **椭圆参数语义与 Phaser 相反**：Phaser `fillEllipse(x,y,w,h)` 收**直径**，
    Cocos `ellipse(cx,cy,rx,ry)` 收**半径**。照搬 web 数值的地方都要 `÷2` ——
    漏了不报错，只是"光晕/伞盖整整大一倍"，看起来"也挺正常"，最难查。
    统一在 `view/neon.ts` 的 `glowPool` 里收口。
14. **`Graphics.roundRect(x,y,w,h,r)` 的 `(x,y)` 是"最小角"**（y 向上的左下角），
    不是左上角。所以 `Gfx.roundRect()` 跟 `Gfx.rect()` 一样要把 y 翻到下边缘；
    漏了会得到一个上下镜像、位置差一个 `h` 的圆角框。
15. **`Graphics` 的 `fill()/stroke()` 只消费"上次收口之后新增的路径"**，
    之前画过的顶点已经烘焙进顶点数据、不会重画也不会清掉。
    所以"同一形状连画三层发光"必须**每次重新组一遍路径**
    （`view/neon.ts` 的 `neon()` 就是这么做的）；反过来，不 `clear()` 就画下一帧，
    上一帧的图形会原地留着 —— 这是切界面时"上一局的画面没消失"的原因
    （`DiveGame.update` 的标题分支必须照样 `clear()` 各层）。
16. **在编辑器运行时"新增一个被 import 的模块"，会留下一个死结：编辑器里全黑，
    而上面 7 个阶段全是绿的。**（2026-10-13 真实踩到）
    机制：Creator 的增量编译在**解析失败时不登记依赖边**。于是那个 importer 永远
    不会因为新模块出现而被重编译，它带着那条失败的 import 一直躺在缓存里。
    链式后果：`view/save.ts` 加载失败 → `DiveGame.ts` 的 import 链断 → 场景里挂的
    组件变成 `Missing class` → **一片全黑**（控制台只说"脚本缺失"，不说是哪条 import 断的）。
    实际经过：`save.ts` 于 12:44 编译，**当时 `shared/dive/profile.ts` 还没同步到磁盘**；
    12:45 文件到位，但 `save.ts` 的 chunk 一直停在 12:44 那一版。
    · **判据**：`cocos/temp/programming/packer-driver/targets/editor/resolution-detail-map.json`
      里的 `__unresolved_*` 条目 —— 这是那个死结**唯一的留痕**，
      现在 `verify_cocos.py` 的「模块图自检」阶段会直接红在这。
    · **解法**：改一下那个 importer 文件的**内容**（不是 `touch`），或删掉
      `cocos/temp/programming` 让它全量重建。
    · **不对称性**：**修改**一个已存在的文件总会触发重编译（依赖边是完整的），
      所以这个坑只出现在"**新**文件"上 —— 顺序务必"先落文件、再写引用"。
17. **椭圆半径/直径的坑会复发**（第 13 条的具体案例）。2026-10-13 又抓到两处
    照抄 web 数值没 `÷2` 的：`drawEnemies` 的深层描边环、以及受击白闪椭圆。
    根因是 `Gfx.ellipse` 把参数命名成 `rx/ry` 也**拦不住**"照着 web 的数字搬"。
    规则：从 `web/src/` 抄任何 `*Ellipse(w, h)` 的数值，**落地时必须 `÷2`**。
18. **兄弟节点的顺序就是绘制顺序**（文件头那张节点树图就是设计）。调整顺序时
    **同步改文件头**，否则注释会开始撒谎。2026-10-13 抓到一次：注释写着
    "发光核心必须画在贴图之上"，而 `gEnt`（发光核心所在层）却排在 `fishLayer`
    **之前** —— 每条鱼的定位核心被自己的贴图精准盖住。**放反了不报错**，
    只在 L3-L5 深色层里表现为"小鱼看不见"。
19. **Creator 打开工程时会"规范化重写" `Dive.scene`**：补全 `_lpos/_lrot/_lscale/
    _mobility/_layer/_euler/__editorExtras__` 等默认字段并重排 `__id__`
    （本次 +142/−69 行）。这是预期行为，**直接入库**即可，入库后再次打开就不会再抖。
    但由此 `tools/gen_cocos_scene.py` 只用于**新建**场景 —— 它是脚手架，
    不再等于仓库里这份（别拿它去"重新生成"已有场景）。
