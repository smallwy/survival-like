## 踩坑记录（重要）

- **Python 文本模式写文件会把 LF 改成 CRLF**（Windows 下 `open(p,'w')` 写 `\n` 会转成 `\r\n`）。本次用它做批量替换，导致 DiveScene.ts 从 4550 行 LF 变成 4999 行 CRLF，git diff 虚增到 9549 行、完全没法审。**以后改源码一律用 Edit 工具，或写完后用二进制模式 `d.replace(b'\r\n', b'\n')` 修回去。**
- 商店卡内分区必须用**相对卡顶的偏移**。曾把 `priceY()` 写成含 `y0` 的绝对坐标，绘制处又 `c.y +`，多乘一次卡顶 y，状态行被推到 y=562 压在价格底板上。
- 商店文字溢出/重叠的审计判据：用「文字包围盒中心是否落在卡内」筛卡内文字，再量四方向伸出量。只比边界会把顶栏提示行、底栏按钮全算进来（误报过 4 条）。

## V6.11：修三个「UI 消失 / 反馈缺失」的根因（同源于 setScrollFactor(0) 不免疫 zoom）

用户本轮 5 条反馈里，③无扣血飘字 / ③白色亮框 / ⑤HUD 不见了 **是同一类回归 bug**。
已修 3 条并实机验证；①炮塔形态、④商店立绘 待用户定方向。

### 主线根因：`setScrollFactor(0)` 只免疫相机「滚动」，**不免疫「缩放」**
主相机带 CAM_ZOOM=1.25 且 centerOn(玩家)，所有贴屏 UI 于是以屏幕中心为原点
被放大 1.25 倍。实测视口 1304×749：左上深度文字 x→−133、顶部氧气条 y→−49、
底部武器条掉出下缘 —— HUD 几乎全出屏。**修法**：新增 `uiCam`（zoom 恒 1）专管
UI；世界对象 `uiCam.ignore([bg,g,gTurret,subImg])`，UI 对象 `cameras.main.ignore`。
- `txt()` 池按 `cat` 分流：'float'→世界相机+scrollFactor(1)；'ui'→UI 相机+scrollFactor(0)。
  对象**创建时一次性定型**，避免动态 ignore 的坑。
- `addHit/addHoverHit` 热区矩形 → UI 相机（顺带修正 zoom 下点击错位）。
- fish 贴图动态创建 → `uiCam.ignore`。

### 第二个真 bug：飘字被 hideTexts 清空
`update()` 顺序 = `draw()`（含 drawFloats，点亮飘字）→ `drawHud()`（含 hideTexts）。
旧 hideTexts 把**整池**设 invisible → 飘字刚点亮就被清掉 → **受击永远看不到伤害数字**。
修：hideTexts 只隐藏 `cat !== 'float'`；飘字隐藏移到 drawFloats 开头（先全隐再点亮存活项）；
弹窗相位 else 分支额外清飘字。

### 第三个：飘字坐标系错位
`spawnFloat(e.x, e.y)` 传世界坐标却挂在 scrollFactor(0) 上 → 相机一滚动就偏出敌人/出屏。
修：飘字归世界相机。顺带修 startWave 开场提示（原用屏幕坐标 → 改 `px, py - H*0.24`）。

### 第四个：受击「白色亮框」→ 本体抖动
`drawSub` 的 `pcol = hurtFlash>0 ? WHITE : cyan` 让 rim 椭圆整圈变白 = 用户说的白框。
按用户原话改为：pcol 恒 cyan；本体（含座圈/炮塔/探照灯锥，都基于 X/Y）在 0.35s 内
做 ±3.5px 抖动。

`tools/shots/fix_子弹.png`：3 门机关枪时 15 颗弹体在飞，橙黄曳光（4 层拖尾+光晕+亮核）

### ★★ 抠底脚本 `tools/process_item_art.py` 改成**按背景类型分流**（这轮踩了 4 个坑）
这一张重出的图把前面写死的阈值全打穿了，暴露出**同一个脚本要处理两类背景**：

| 背景类型 | 判据（四角 64×64 的**标准差**） | 抠法 |
|---|---|---|
| **平底**（纯白/带渐晕浅灰） | std ≈ 1.3~1.7 | 亮度门槛 = 参考亮度−32、饱和度门槛 = 参考饱和度+13，**从四边泛洪 + 邻接推进**（步长 12）；武器外圈深色描边是墙 |
| **棋盘格**（生成器把"透明"画成棋盘） | std ≈ 10 | 结构性判据：**任一局部窗口两种格色都出现**（窗口 20、各自占比 >15%）→ 背景；机身白是一整片单色 → 不是背景 |

坑（按踩的顺序）：
1. **写死 `lum>232`**：新图是带渐晕的灰底（四角 238、边缘最暗 216）→ 泛洪只铺 2.9%，
   成品的背景整块留着（实机一块浅灰方块）。
2. **把阈值放宽到 205 救电弧** → **反过来把酸液的浅绿罐体吃掉**（内容 577→393 宽）。
   根因：罐体浅绿的**反锯齿过渡带**饱和约 27，是个"低饱和桥"。→ 改成自适应
   `饱和门槛 = 参考饱和度 + 13`（白底图自动收到 14，挡住桥）。
3. **邻接推进步长卡在 12** → 棋盘格相邻两格亮度差约 19（247/228）**跨不过去**，
   泛洪只在起始格打转，成品留了一整块 **783×516 的完美矩形**。
4. **把步长放到 64** → 跨过棋盘格了，但**也跨进了白机身**（机身 230 vs 背景 245，差 15）：
   电弧只剩闪电、回声被啃掉一块。
   → 结论：**步长这一个参数不可能同时满足两类背景**，必须分流。

### 另一个坑：`keep_largest` 会丢掉独立部件
电弧的**电极臂与紫色闪电**和炮身是不连通的独立连通域，只保留最大块会把它们一起丢掉
（内容宽度 780 → 404）。改成 `keep_components`：保留**所有面积 ≥ 最大块 3% 且 ≥64px**
的连通域 —— 噪点/水印照样清掉，独立部件留下。

### 排查方法（值得复用）

（`Image.fromarray(alpha,'L')`），并打印"逐行/逐列不透明像素最多的位置"——
一眼就能看出成品是一块**矩形**（= 泛洪失败）还是**武器形状**（= 成功）。

## 关卡深度专项复核（用户提问：「只有几层设计 这种深度不够吧」）

### 先纠正前提：这个品类**没有关卡地形**
核代码：`obstacle / collide / blocker / 岩壁` 在 `DiveScene.ts` 里 **0 处引用** —— 竞技场是空地。
Brotato / DRG:S 都没有地形遮挡，所以"没有关卡设计"在这个品类里≠缺陷。
品类里的"关卡设计" = ① 波次编排 ② 层差异(modifier) ③ 敌人组合。

### 核对出的真问题（两条，都是"深度不够"的真根因）
1. **`WAVE_SHAPE` 是全局一张 4 项表**（`count/dashRatio/hpMul/dur`），按 `waveInLayer` 索引
   → **5 层共用同一套波次节奏**，只被层的 `cntMul/hpMul` 放大。这是首要原因。
2. **5 层里只有 L4 有一个真机制**：`ventPush`（热泉推流，190）。其余 11 个字段
   （氧气上限/消耗/掉落上限/血量/数量/冲刺占比/水母占比/视野/色调/粒子/深度区间）
   **全是数值缩放** → 层 ≈ 同一关加数值 + 换色。

另：敌人 3 类 vs 计划书 §3.5 要 4 类。

### 我给的推进方案（写进 `docs/后续工作计划_V6.23.md` §6.3）
1. **`WAVE_SHAPE` 1×4 → 5×4**（纯数据表，最便宜，直接解决"每层一样"）
2. **每层加一条层规则**（L2 暗流推玩家 / L3 单方向涌流 / L5 压力=氧气继续压缩；L1 留空做教学）
3. 补第 4 类敌人（重甲/护盾）
4. 可选：层内随机事件

**重要**：这一块**不影响 §10 止损线判定**（那条只看"单波爽不爽 + 氧气要不要捡"），
影响的是"单局 20-25 分钟的耐受度" → 归入 P2，**P0 止损线仍排最前**。
