# 分辨率自适应 & 高 DPI 清晰度（V6.27）

> 用户反馈原话：
> 「1 方案选 A 并且要适应切图  2 我改变分辨率不能自适应吗 会出现黑色边界 视野遮挡」
>
> 本文解决第 2 条（分辨率自适应 / 黑边 / 视野遮挡），并说明它与第 1 条（键帽要能适配切图）的关系。

---

## 一、结论先行

**黑边的真根因不是「分辨率没适配」，而是旧的高 DPI 实现把 `gameSize` 改成了物理像素、
却没同步相机尺寸**，导致世界只画在画布左上角 1/DPR² 的区域。

正确的做法反而是**不动 `gameSize`**：保持 `gameSize = canvas = CSS`（Phaser RESIZE 的默认行为），
再给画布加一条 `image-rendering: pixelated`，让高 DPR 屏的合成器用**最近邻**把 CSS 位图
放大到物理像素。这样：

- **零黑边**（画布位图 = `gameSize`，相机永远铺满）；
- **UI 尺寸永远正确**（所有按 CSS 像素布局的卡宽 / 字号都按设计值显示）；
- **像素风保持清晰**（最近邻放大 = 硬边像素块，和游戏自身的 NEAREST 纹理采样一致）。

---

## 二、源码级根因（Phaser 3.90）

### 2.1 渲染器的「分辨率」恒为 1

Phaser 3 的 WebGL 渲染器没有分辨率倍率。相机的视口与裁剪矩形**直接把 `camera.width/height`
当设备像素用**：

```js
// node_modules/phaser/src/renderer/webgl/WebGLRenderer.js
preRenderCamera: function (camera) {
    var cw = camera.width;   // 单位 = 游戏（逻辑）像素
    var ch = camera.height;
    this.pushScissor(cx, cy, cw, ch);   // 直接当设备像素
    ...
}
// pushScissor → gl.scissor(x, y, width, height)   // 无 resolution 乘子
```

也就是说：**相机占多少个设备像素 = 相机的逻辑宽高**。要让相机铺满画布，
`camera.width`（来自 `gameSize`）必须等于画布位图宽度。

### 2.2 因此 `gameSize ≠ 画布位图` 必然出黑边

若把 `gameSize` 设成 CSS、画布位图设成物理（曾尝试的 `logical` 方案）：
相机视口 = CSS 像素，画布位图 = 物理像素 → 相机只覆盖画布左上角 `1/DPR²`，其余露清屏色。
**这就是「黑色边界 + 视野遮挡」。** 该方案在源码层面就不成立，已废弃。

### 2.3 相机重设尺寸的触发条件

```js
// node_modules/phaser/src/cameras/2d/CameraManager.js
onResize: function (gameSize, baseSize, displaySize, previousWidth, previousHeight) {
    var cam = this.cameras[i];
    if (cam._x === 0 && cam._y === 0 && cam._width === previousWidth && cam._height === previousHeight) {
        cam.setSize(baseSize.width, baseSize.height);   // ← 用 baseSize，不是 gameSize
    }
}
```

旧 `zoom` 实现把 `gameSize` 改成物理像素后，**用 `physW` 当 `previousWidth` 重发 resize 事件**，
而相机此刻还是 CSS 尺寸 → `cam._width === previousWidth` 不成立 → 相机停在 CSS、
画布已是物理 → 世界缩到左上角。**这是黑边的直接触发点。**

> 修法二选一：① `previousWidth` 传 CSS 尺寸；② 干脆不用 `zoom` 模式（本就不存在错位）。

## 三、三种 DPR 策略对比（实测 / 源码双验证）

| 策略 | gameSize | 画布位图 | UI 尺寸 | 清晰度 | 黑边 | 结论 |
|---|---|---|---|---|---|---|
| **none**（现默认） | CSS | CSS | ✅ 正确 | ✅ 靠 `image-rendering:pixelated` 最近邻放大 | ✅ 无 | **采用** |
| zoom（旧实现，opt-in） | 物理 | 物理 | ❌ 缩到 1/DPR | ✅ 纹理物理渲染 | ⚠️ 修 previousWidth 后无，但尺寸仍错 | 仅保留作对比 |
| ~~logical~~（已废弃） | CSS | 物理 | —— | —— | ❌ 必出黑边 | 删除 |

`zoom` 的致命问题：商店卡宽 248、字号 13~22px 都是**按 CSS 像素写的常量**，
一旦 `gameSize` 变成物理，它们就按 `1/DPR` 显示 —— 高 DPR 屏上整个商店/世界
缩成屏幕中央一小团。这正是用户说的「不适应切图」。

## 四、最终实现（`web/src/main.ts`）

```ts
function installDprScale(game: Phaser.Game): void {
  const sm = game.scale
  const mode = new URLSearchParams(location.search).get('dprmode') || 'none'
  const canvas = sm.canvas
  // 关键：合成器最近邻放大（高 DPR 下像素风保持硬边）
  canvas.style.imageRendering = 'pixelated'

  const origRefresh = sm.refresh.bind(sm)
  ;(sm as any).refresh = () => {
    origRefresh()
    // none：gameSize=canvas=CSS，默认行为已正确，直接返回（零黑边）
    // zoom（?dprmode=zoom）：framebuffer=物理、ScaleManager.zoom=1/DPR，
    //   注意 previousWidth 必须传 CSS 尺寸，否则相机错位 → 黑边
    ...
  }
}
```

配套：文字光栅倍率在 DPR>1 时提到 `2*dpr`（钳 6），抵消合成器最近邻放大带来的「脆」。

## 七、遗留 / 后续

1. **`zoom` 模式**保留为 `?dprmode=zoom` 的 opt-in（追求极限纹理清晰度），
   默认不用。若能接受「内容按 1/DPR 缩小」，可手动开启对比。
2. **文字在 DPR=2 下**采 `2*dpr` 光栅 + 最近邻放大，锐但略「脆」；
   若后续要更平滑的文字，需要把 UI 与像素世界拆到两张画布（工程量大，暂不做）。
3. **4K + DPR2** 的纯软件渲染较慢，无头诊断里 1920×1080@DPR2 耗时明显；
   真机 GPU 无此问题。
