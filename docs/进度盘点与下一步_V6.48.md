## 2. ★ 满屏压测（本轮新增）

**红线原文**（计划书 §7）：「同屏 **150 敌人 + 50 拾取物** → **60 FPS**」，§10 列为中等风险。

**怎么测的**：`tools/dive_sim_bench.js` 把 `shared/dive` 编译成 CJS 真跑（和 `dive_sim_smoke.js` 同一条链），
每个场景 900 帧、预热 120 帧，世界状态钉死在 `wave` 相位。

> ⚠️ 第一版写出过"空转 0.0005ms"这个**假数** —— 0 敌人时清波判定立刻成立，phase 滑进 `shop`，
> 而商店相位只跑 `updateBones`，等于什么都没测。修法：压测里把 `updateWave` 摘成空函数。
> **教训与项目铁规 #7 同源：没报错 + 跑得快 ≠ 测到了东西。**

### 2.1 模拟层：离瓶颈还差两个数量级

| 场景 | 敌人 | 鱼骨 | 平均 | p95 | 占 60FPS 预算 |
|---|---|---|---|---|---|
| A0 空转 | 0 | 0 | 0.004 ms | 0.006 | 0.0% |
| A2 敌人 | 150 | 0 | 0.160 ms | 0.249 | 1.5% |
| **A3 ★ 红线** | **150** | **50** | **0.149 ms** | **0.243** | **1.5%** |
| **A4 ★ 红线 + 机制武器** | **150** | **50** | **0.093 ms** | **0.168** | **1.0%** |
| A5 超载 | **300** | 50 | 0.314 ms | 0.451 | 2.7% |

**缩放是严格线性的**：每敌 ~**1.0 µs** 恒定（25→300 敌全程不变）。300 敌实测 ×6.67，线性外推 ×6 —— **没有超线性拐点**。

**两个新引入的"按敌数伸缩"路径，实测都无害**：

| 路径 | 最坏值 | 实际 |
|---|---|---|
| `enemyAim()` 每敌每帧 | 全员策反（k = n = 150）时 **0.053 ms/帧** | 网 `iv` 1.1s、策反 4s ⇒ 通常 k ≤ 4，这是 **40× 余量的上界** |
| `densestSpot()` O(n²) | n=150 时 **0.0034 ms/次** | 只有诱饵开火才调用（~2.4s 一次）⇒ 摊薄 <0.01 ms/帧 |

**尖刺归因**：最慢 1% 帧是 0.14 → 0.40 ms，但**伴随实体数一点没涨**（事件 9→11、子弹 30→30、敌人 150→150）
⇒ 尖刺来自 **分配 / GC**，不是某个子系统在那一帧变重。不必针对性优化。

### 2.2 渲染层：沙箱量不了，但能**算**

⚠️ 上面那 1.5% **不能读成"60FPS 成立"**。真正吃帧预算的是 Cocos 的 `Graphics` 重绘，沙箱跑不了。
但渲染层的**图元预算**是静态可算的（读码得出，非实测）：

| 渲染项 | 每单位图元数 | 红线帧（150 敌 / 50 骨 / 30 弹） | 出处 |
|---|---|---|---|
| **鱼骨** | **9**（3 圈辉光 + 脊柱 + 4 肋 + 头端亮核） | **450** ← **最大单项** | `DiveGame.ts:1772-1795` |
| 敌人（矢量兜底） | 2（fillTri + 2px 核心） | 300 | `DiveGame.ts:1944-1959` |
| 子弹 | 3–6（弹体 + 尾迹） | ~100–180 | `DiveGame.ts:1824-1913` |
| 被控敌人状态标记 | 最多 17（网 6 弧 + 索 3 + 灼烧 2 圈 + 内讧 3） | 只落在少数被控目标上 | `DiveGame.ts:1967-2000` |
| 环境/波前/爆炸/火花/玩家件 | — | ~150–250 | `gBack` / `gFx` / `gPlayer` |

⇒ **红线帧的量级是 1000–1200 个 `Graphics` 图元/帧**，其中**鱼骨占 450，比 150 只敌人（300）还多**。

**而且 150 敌这条线正好卡在两个阈值之上**：

| 阈值 | 值 | 后果 |
|---|---|---|
| `DiveGame.ts:954` | `enemies.length > 120` → 返回 null | 150 敌 **全部走矢量兜底**，贴图通道关闭 |
| `DiveGame.ts:177` | `FISH_CAP = 140` | 即便改上一条，鱼池也**装不下 150 条** |

这两条本身是合理的 LOD 设计（贴图是逐条 sprite，量大不划算）。但它们意味着：
**"150 敌"这个特定数字，恰好是渲染层最差的一档 —— 视觉精度最低、CPU 图元最多。**

### 2.3 结论与建议（三条，按性价比）

| # | 动作 | 省下 | 风险 |
|---|---|---|---|
| **①** | **鱼骨辉光 3 圈 → 1 圈**（`DiveGame.ts:1778-1780`，外两层 `0.10` / `0.16` alpha 的氧青光晕合成一层） | **100 图元/帧**，且视觉几乎不可辨（两层都是低 alpha 同心圆） | 极低（纯参数） |
| **②** | **A/B 实测贴图 vs 矢量**：临时把 `954` 的阈值与 `FISH_CAP` 一起提到 160，在 Creator 里对同一帧截图比 profiler | 未知，但**方向可能是反的** —— Cocos 同图集 Sprite 能合批，150 sprite 也许比 150 次 `fillTri`（各自建路径 + 全网格重建）更便宜 | 需实机；**这正是要在 Creator 里看的那一件事** |
| **③** | 深层 `lod` 已有两档（`n>80→2`），可再加一档 `n>140` 只画核心不画 body | 若①够用则不必做 | 低，但会掉可读性 |

> **为什么把鱼骨排在敌人前面**：鱼骨是**纯装饰**（唯一功能是"发光 = 能捡"），
> 而它每块画 3 个同心圆只为了做辉光衰减 —— 3 圈低 alpha 圆在观感上等价于 1 圈。
> 敌人降到 2 图元已经是硬底（再省就读不出是鱼了）。**先砍不心疼的那 450 里的 100。**

### 2.4 复现

```bash
# 编译模拟核心（与 verify_cocos.py 用同一条链）
node web/node_modules/typescript/bin/tsc shared/dive/index.ts \
     --outDir .tmp/sim-build --rootDir shared --module commonjs --target ES2020 \
     --moduleResolution node --strict --skipLibCheck --lib ES2020,DOM

# 跑压测（可选 --json 落盘）
node tools/dive_sim_bench.js .tmp/sim-build --json .tmp/bench.json
```
